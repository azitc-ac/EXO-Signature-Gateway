Nach der Bearbeitung gibt das Gateway jede Mail an Exchange Online zurück. Hier legst du Ausnahmen fest: Post für bestimmte Empfänger geht an einen anderen Server, oder das Gateway stellt sie selbst zu.

Die Regeln werden in dieser Reihenfolge geprüft: Absender-Tenant → Empfängerdomäne → externe Empfänger. Die erste passende Regel gilt, alles andere geht an Exchange Online. Den laufenden Betrieb des SMTP-Relays findest du unter SMTP-Relay.

Zielserver

Server, an die das Gateway Post übergeben kann, etwa ein lokaler Mailserver, ein zweites Gateway oder der Dienst eines Anbieters. Ein Zielserver allein bewirkt nichts; erst eine Regel unten schickt Post dorthin.

Regeln

⚠️ Die Regeln für Empfängerdomänen und externe Empfänger wirken nur mit dem Rückweg „SMTP Port 25“. In den Graph-Modi geht diese Post an Exchange Online. Die Regel für den Absender-Tenant wirkt immer.

Nach Absender-Tenant

Post aus einem anderen Microsoft-365-Tenant weist das Gateway sonst ab. Steht der Tenant hier, geht seine Post vor jeder Bearbeitung unverändert an das Ziel. Erkannt wird der Tenant an seiner Kennung, die Exchange Online in den Kopf schreibt (X-MS-Exchange-CrossTenant-Id), nicht an der Absenderdomäne. Ist das Ziel nicht erreichbar, stellt Exchange Online später erneut zu.

Externe Empfänger

Post an Adressen außerhalb deiner Domänen, für die keine Domänenregel greift, geht an das gewählte Ziel, zum Beispiel an direkt (siehe Selbst zustellen). Interne Empfänger bleiben bei Exchange Online.

Selbst zustellen

Das Gateway kann Post auch selbst zustellen, direkt an den Mailserver des Empfängers oder über einen Smarthost. Welche Post diesen Weg nimmt, bestimmen die Regeln mit dem Ziel direkt.

⚠️ Läuft das Gateway in Azure, AWS oder einer ähnlichen Cloud, ist Port 25 ausgehend dort in aller Regel gesperrt. Zustellen geht dann nur über einen Smarthost. Beim Speichern mit „Selbst per MX zustellen“ prüft das Gateway den Port und fragt nach, wenn er gesperrt ist.
⚠️ Damit Empfänger die Post annehmen, braucht jede Absenderdomäne einen DKIM-Schlüssel (unten), die Ausgangsadresse im SPF-Eintrag und möglichst einen PTR, der zum HELO-Namen passt.

Tägliche Probe

Einmal am Tag schickt das Gateway eine Mail über diesen Weg an ein internes Postfach. Sie kommt über den eigenen MX zurück wie Post von außen. Geprüft werden Ankunft, Ordner (Junk?) und SPF/DKIM/DMARC; danach wird sie gelöscht. Grün nur, wenn sie angekommen ist und alle drei bestanden hat.

Ein internes Postfach, z. B. ein geteiltes. Liest und löscht die App per Graph — bei RBAC for Applications muss es im erlaubten Bereich liegen.
Wird geladen …
Empfehlung, keine Pflicht: Lege je ein Testpostfach bei Gmail und Outlook.com an und trage es hier ein (höchstens 5, durch Komma getrennt). Die interne Probe zeigt nur, ob Post bei dir ankommt. Große Anbieter beurteilen eine Versand-IP auch nach ihrer Vorgeschichte; Gmail etwa rät neuen Absendern, mit wenig Post zu beginnen, und weist bei zu viel vorübergehend ab. Eine Probe dorthin zeigt, ob deine Post angenommen, verzögert oder abgelehnt wird. „Zugestellt“ heißt nur, dass der Server des Anbieters sie angenommen hat — ob sie im Posteingang oder im Junk liegt, sieht das Gateway nicht.

Wenn das Ziel ein lokaler Exchange ist

Ein lokaler Exchange nimmt Post vom Gateway nur dann als intern an, wenn er dem Gateway vertraut. Das Skript unten richtet dafür einen Empfangsconnector ein (Inbound from <Gateway> (Coexistence)) und baut ihn bei Bedarf wieder ab. Das Gateway führt es nicht selbst aus; du startest es in der Exchange Management Shell.

⚠️ Sicherheit: Der Connector vertraut jedem Absender hinter der angegebenen Quell-IP. Das ist nur vertretbar, wenn über diese Adresse ausschließlich das Gateway einliefert. Steht ein Load-Balancer mit Adressumsetzung (SNAT) davor, ist die Quell-IP die des Load-Balancers, nicht die des Gateways.
