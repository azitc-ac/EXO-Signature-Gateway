Ohne Direktversand bleibt Post an externe Empfänger im Notfall in der Warteschlange.

Im Ernstfall

  1. Notfall ausrufen (oben) — ab dann geht Post in die Kopie statt an Exchange.
  2. Beim DNS-Anbieter den MX jeder Domäne auf dieses Gateway stellen (kurze TTL vorab hilft).
  3. In der Firewall Port 25 aus dem Internet zum Gateway öffnen (sonst nur Microsoft).
  4. Den Mitarbeitern das Notfall-Webmail nennen: {{ webmail_url }}
  5. Unter Bereitschaft „Jetzt prüfen“: Der MX muss auf das Gateway zeigen.

Nach der Störung

  1. MX zurück auf Exchange Online, Port 25 wieder nur für Microsoft.
  2. Notfall beenden (oben).
  3. Unter Kopie für den Ernstfall „Zurückspielen“ — Post aus dem Notbetrieb geht nach Exchange; doppelt Eingespieltes wird erkannt.

Vor dem Notfall: kennenlernen und üben

Anmelden kann sich jeder jederzeit — so richten alle den Zugang vorab auf ihren Geräten ein. Inhalte zeigt das Webmail vor dem Notfall nur der Probegruppe; alle anderen sehen „bereit“ — außer du gibst die Kopie unten für alle frei.

So sieht jeder, was im Ausfall da wäre, und kennt die Oberfläche schon. Das Webmail zeigt oben, wie alt die Kopie ist und wie weit sie zurückreicht. Gesendetes legt das Gateway selbst unter „Gesendete Elemente“ nach Exchange zurück — derselbe Weg wie nach einer Störung, nur laufend.

Eine Adresse je Zeile. Liest und sendet schon jetzt wie im Notfall: sieht die Kopie auch ohne „für alle lesbar“ und sendet am Exchange vorbei (Probealarm: externe per Direktversand, interne nur in die Kopie).

Was sieht jemand im Notbetrieb?

Post von außen im Notfall

Solange der Notfall ausgerufen ist, nimmt das Gateway Post aus dem Internet an — nur für Postfächer des eigenen Tenants, alles andere wird schon beim Empfänger abgewiesen (kein offenes Relay). Damit sie ankommt, zeigt der MX der Domäne auf das Gateway und die Firewall lässt Port 25 aus dem Internet durch; beides ist im Normalbetrieb nicht so und wird nach der Störung zurückgestellt. Geprüft werden SPF, DKIM und DMARC: abweisen, was die Absenderdomäne so verlangt oder sich als eigene Domäne ausgibt, Zweifelhaftes in Junk-E-Mail. Noch ohne Inhaltsfilter.

On-Prem-Postfächer

Liegen Postfächer noch auf einem eigenen Exchange-Server (gemeinsamer Namensraum: Exchange Online führt sie als externe Benutzer mit eigener Adresse), leitet Exchange Online deren Post im Normalbetrieb dorthin. Im Notfall übernimmt das Gateway — über einen Zielserver aus Einstellungen → Mail-Routing. Weitergeleitet wird nur, was im Abbild als On-Prem-Postfach steht, nie eine ganze Domäne. Gibt es für die Domäne schon eine Route auf einen Zielserver, gilt diese. Ohne Ziel weist das Gateway solche Post im Notfall ab bzw. legt sie in die Warteschlange; nach der Störung stellt Exchange sie zu.

Webmail auf die Geräte bringen

Im Notfall installiert niemand mehr etwas — bring die Notfall-Mail vorher auf die Geräte. Die Nutzer öffnen die App und werden geführt: Im Normalbetrieb zeigt sie „Dein Notfall-Zugang“ — Microsoft-Anmeldung, dann Passkey oder Authenticator-App einrichten. Im ausgerufenen Notfall zeigt sie zuerst die Anmeldung. Niemand braucht eine Adresse. Verteile immer diese, Passkeys gelten nur für den Namen, unter dem sie eingerichtet wurden: {{ webmail_url }}.

Anmeldung im Notbetrieb

Im Störfall ist womöglich auch Entra nicht erreichbar. Die Nutzer melden sich dann mit ihrem gewohnten Kennwort an; das Gateway prüft es direkt am Domänencontroller (LDAP, nur verschlüsselt). Es braucht kein Dienstkonto und speichert kein Kennwort.

Den Namen aus dem Zertifikat des DC eintragen — geprüft wird gegen ihn. Eine IP-Adresse geht nur, wenn sie im Zertifikat steht. Löst der Name hier nicht auf: Hosts-Eintrag anlegen.

Zweiter Faktor

Kennwort allein reicht nicht: Dazu kommt ein Passkey (Fingerabdruck, Gesicht, Windows Hello, Sicherheitsschlüssel) oder ein Code aus einer Authenticator-App (TOTP). Eingerichtet wird er im Normalbetrieb nach einer Microsoft-Anmeldung, damit nur die Person selbst ihn einrichten kann — unter {{ webmail_url }}/einrichten. Auch das prüft das Gateway ohne Cloud. Microsoft verlangt dabei eine frische Anmeldung; wer dort noch keine MFA-Methode hat, wird zuerst durch deren Einrichtung geführt.

Ein Passkey gilt nur für den Namen, unter dem er eingerichtet wurde. Ändert sich der Name des Gateways (oder öffnet jemand das Webmail unter einem anderen Namen oder per IP-Adresse), bleibt dort nur der Code aus der App oder ein Wiederherstellungscode. Verteile deshalb immer denselben Link.
