Notfall

{% if ausgerufen %}
Der Notfall ist ausgerufen. Was das Gateway sonst an Exchange übergibt, landet in der Kopie bzw. geht per Direktversand hinaus. Nach der Störung ausschalten und zurückspielen.
{% endif %}

Schalte um, wenn Exchange Online ausgefallen ist. Interne Empfänger bekommen ihre Post dann in die Kopie (lesbar im Notfall-Webmail), externe über den Direktversand. Ohne Direktversand bleibt Post an externe Empfänger in der Warteschlange.

Vor dem Notfall

Anmelden kann sich jeder jederzeit — so lässt sich der Zugang vorab auf allen Geräten einrichten. Inhalte zeigt das Webmail vor dem Notfall nur der Probegruppe (für Probealarme); alle anderen sehen „bereit“. Eine Adresse je Zeile.

Bereitschaft

Würde der Notbetrieb jetzt funktionieren? Geprüft werden Kopie, Rechte, Profile, Anmeldung am Domänencontroller, Versand nach außen und Zertifikat — dazu, wohin der MX jeder Domäne zeigt.

Ablauf im Ernstfall

  1. Oben Notfall ausrufen — ab dann geht Post nicht mehr an Exchange, sondern in die Kopie.
  2. Beim DNS-Anbieter den MX jeder Domäne auf dieses Gateway stellen (kurze TTL vorab hilft).
  3. In der Firewall Port 25 aus dem Internet zum Gateway öffnen (im Normalbetrieb nur Microsoft).
  4. Den Mitarbeitern die Adresse des Notfall-Webmails geben: /notfall auf diesem Gateway.
  5. „Jetzt prüfen“: Der MX muss auf das Gateway zeigen.

Nach der Störung

  1. MX zurück auf Exchange Online, Port 25 wieder nur für Microsoft.
  2. Den Notfall beenden.
  3. Zurückspielen — Post aus dem Notbetrieb geht nach Exchange (doppelt Eingespieltes erkennt es).

Was sieht jemand im Notbetrieb?

Post von außen im Notfall

Solange der Notfall ausgerufen ist, nimmt das Gateway Post aus dem Internet an — nur für Postfächer des eigenen Tenants, alles andere wird schon beim Empfänger abgewiesen (kein offenes Relay). Damit sie ankommt, zeigt der MX der Domäne auf das Gateway und die Firewall lässt Port 25 aus dem Internet durch; beides ist im Normalbetrieb nicht so und wird nach der Störung zurückgestellt. Geprüft werden SPF, DKIM und DMARC: abweisen, was die Absenderdomäne so verlangt oder sich als eigene Domäne ausgibt, Zweifelhaftes in Junk-E-Mail. Noch ohne Inhaltsfilter.

Zugang für Mailprogramme (IMAP und SMTP)

Outlook (als zusätzliches Konto) und Mail-Apps auf dem Handy lesen die Kopie per IMAP — nur lesend — und senden per SMTP über das Gateway, mit Signatur wie im Webmail. Vor dem Notfall zeigt das Konto einen leeren Posteingang und sendet nicht (außer für die Probegruppe), es kann also vorab auf allen Geräten eingerichtet werden.

Kontodaten: Server {{ imap_host or 'Hostname dieses Gateways' }}, eingehend IMAP Port 993 (SSL/TLS), ausgehend SMTP Port 587 (STARTTLS, Anmeldung erforderlich), Benutzername und Kennwort wie bei der Windows-Anmeldung. Die Firewall muss beide Ports zum Gateway durchlassen. Als Server immer den Namen eintragen, nie die IP-Adresse: Er muss zum Zertifikat passen, sonst lehnt das Programm die Verbindung ab — Outlook bricht das Senden dann womöglich ohne Rückfrage ab. Gesendet wird aus dem eigenen Postfach oder einem mit „Senden als“/„Senden im Auftrag“; die Kopie unter „Gesendete Elemente“ legt das Gateway selbst ab.

Anmeldung im Notbetrieb

Im Störfall ist womöglich auch Entra nicht erreichbar. Die Nutzer melden sich dann mit ihrem gewohnten Kennwort an; das Gateway prüft es direkt am Domänencontroller (LDAP, nur verschlüsselt). Es braucht kein Dienstkonto und speichert kein Kennwort.

Zweiter Faktor

Kennwort allein reicht nicht: Dazu kommt ein Code aus einer Authenticator-App (TOTP). Eingerichtet wird er im Normalbetrieb nach einer Microsoft-Anmeldung, damit nur die Person selbst ihn einrichten kann — unter https://{{ imap_host or 'Hostname dieses Gateways' }}/notfall/einrichten. Auch das prüft das Gateway ohne Cloud. Solange der zweite Faktor Pflicht ist, nehmen IMAP und SMTP kein reines Kennwort an.
